# ED Explorer Kit — architecture

Local companion app for Elite Dangerous explorers (exobiology + mapping).
A Python backend runs on the player's PC, reads the game journal, stores it in SQLite
and serves a React UI that works on a second monitor or a phone on the LAN.

```
Journal dir ──poll 250 ms──► JournalReader (byte offsets, complete lines only)
   └► one SQLite tx: INSERT events → Projector.apply(event) → projection upserts → COMMIT
          └► SSE "invalidate {topics}" ──► browser refetches /api/view/{topic}
Status.json ──poll──► LiveStatus (memory only) ──► SSE "status"
NavRoute.json ──poll──► PlottedRoute (memory only) ──► SSE "invalidate {navroute, galaxy}"
```

## Backend (`backend/`, Python 3.12, uv, FastAPI)

| Module | Role |
|---|---|
| `app/config.py` | Paths (journal dir, data dir, built frontend: `frontend/dist`, or `web/` inside the exe), port, listen address; `journal_dir_fixed` when the journal folder is set at launch (`--journal-dir`, `EDEK_JOURNAL_DIR`: Docker); `parse_dir` cleans a pasted folder (quotes, `%VARS%`, `~`); `data_dir_fixed` when the data folder is set at launch (`--data-dir`, `EDEK_DATA_DIR`), `data_home` where a chosen one is noted |
| `app/db.py` | SQLite connection, pragmas (incremental auto-vacuum, set before WAL so a new file takes it), schema; caches whose format changed are dropped (`_drop_old_caches`); `compact`: gives freed pages back to the disk at start (a database made before 2026-10-25 is rewritten once by VACUUM to switch auto-vacuum on; the pragma is read to the end: each step frees one page) |
| `app/journal.py` | Journal file discovery, ordering by Fileheader time, tailing by byte offset. Files are known by name (`journal_files`), so a moved folder is not read twice; discovery returns only the files present in the folder (events of files read from another folder stay) |
| `app/status.py` | Status.json reader and flag decoding |
| `app/projector.py` | Applies journal events to projection tables (single writer). A death is a `Died`, or a `LoadGame` with `StartDead` that no `Died` came before: the game does not always write one (2026-10-23: the ship destroyed while the commander sat in the SRV, then the game restarted). A restart on the rebuy screen after a `Died` is the same death (no `Resurrect` yet). Time spent: every event first credits the gap since the one before to where the commander was (`visits.seconds` of the current visit; `body_time` near a planet, `ApproachBody`..`LeaveBody`); a gap over `AFK_GAP_S` (30 min) is AFK, and one ending at `Fileheader`, `Commander`, `LoadGame` or `Shutdown` is the launcher, the menu or quitting: neither counts. It publishes no topic: the views carry `time_as_of` (the last event) and the screens count on from it while the game runs |
| `app/views.py` | Builds `SystemView` (current, visited, or never visited: community data alone, with a `lookup` state) / `SurfaceView` (the body of the run in progress, or the one Status.json puts you near when that is another body: the run is left out until you are back) / `SessionView` from SQLite; body interest/progress, orbit tree data; the session's last sale and docking (station) and `growth`: unsold data when you left each system since the last sale |
| `app/stats.py` | All-time `StatsView` (incl. death history, first discoveries/maps/footfalls) |
| `app/sessions.py` | `SessionsView`: past game sessions. A session is one game run, from the first `LoadGame` to `Shutdown` (or the run's last event after a crash): every launch starts a journal file (`Fileheader` part 1; parts 2+ continue it), so going back to the main menu stays in the session, another commander's `LoadGame` starts a new one. What a session earned is the data gathered in it, sold or not, found by timestamp: bodies by `scanned_at` (the DSS share by `mapped_at`), species by analysis time; data lost on a death since is counted apart, where it was gathered. New codex entries are the game's `IsNewEntry` (it matched the first occurrence in every case of the player's journals) |
| `app/history.py` | `HistoryView`: visited systems (`visits` table) with what you did there and how long you stayed |
| `app/routeplan.py` | Route planning: system value = mapping payouts (Road to Riches kinds) + biology (bodies with bio signals); or, goal "codex", new codex entries (biology only; each entry counts once per route: stops taken nearest first, or greedily along a line, each worth what the stops before it do not cover; an entry on several bodies of a stop counts as on at least one); Spansh body searches, permit / population / value filters (a body's biology in total, and the dearest species that may grow there: `BioEstimate.best`; "skip finished" also leaves out systems where you analysed any species), stop order (nearest neighbour + 2-opt, or along a line) |
| `app/boxel.py` | A system's boxel and its number there from the id64 (mass code, cube corner and size, the id64 of another number) and the generated name without its number; numbers in a boxel run from 0 with no holes, except where catalogue stars took a generated star's place (near Sol) |
| `app/routefirsts.py` | Goal "firsts": systems nobody has likely discovered. Candidates from Spansh's known systems around a point or along a line: those known only from plotted routes (no star, no body: exact position) and one missing number per boxel of mass code a-c (the boxel's centre, `spread_ly` half its edge; not from a boxel with a catalogue or renamed system, nor one partly outside what has been read around a point; asked about by id64 before use). Visited, populated and permit-locked systems are left out. Around a point: the nearest, nearest neighbour + 2-opt; along a line: each stop the candidate furthest along within a full tank's jump (or the line over the stop count) |
| `app/routebio.py` | Exobiology value of Spansh bodies for routes: facts conversion (incl. materials), genus names, species-based (min, max) estimate, and the codex entries each body may give with their chances (a genus confirmed by DSS or deduced 1, a predicted one 0.5 shared among the open signals; candidate species by `exobio.odds`, as on the System tab, colours equally) |
| `app/codex.py` | Your codex: entries by colour variant and by species, with regions; `predicted_status`: a predicted species' state and the share of its likely colours you have not logged in the region |
| `app/spansh.py` | Spansh search client with a SQLite cache (pages stored zlib-compressed, about 7 times smaller; body pages 7 days, systems 7 days, permit list 30 days, the known systems around a place for firsts routes 1 day: `systems_near`, nearest first, each with whether its arrival star and how many bodies are known); asks for gzip (a station carries its whole market); `stations()`: stations offering a service, nearest first; `station_search()`: any station filter, answers as Spansh sends them |
| `app/selling.py` | Where to sell (`SellView`, `GET /api/view/sell[?carriers=true]`): Spansh station searches on a worker thread, per service (Universal Cartographics, Vista Genomics) stations and fleet carriers apart (carriers outnumber stations and would crowd them out), the latest kept in `sell_search` and reused within 20 ly or a tenth of the way to the nearest station found (6 h); plus the stations you docked at (`docks`, also offline). Per system the best station buying both kinds, else the best of each; filtered by the pad your ship needs, by docking rights (`may_dock`: a Powerplay Stronghold Carrier, named so and owned by a Power, only for that Power's pledges; the pledge from the journal's latest `Powerplay` / `PowerplayJoin` / `PowerplayDefect` / `PowerplayLeave`, as `Powerplay` is not written at every login) and by age (`gone`: megaships not heard of for a year, Thargoid-war ships long gone); permit-locked systems marked (Spansh's list, fetched by the worker once after the first search). Carriers only on request (a switch, per browser): closed to the public (Spansh `carrier_docking_access`) or not seen for 30 days never; when hidden, the nearest one nearer than every station is named as a hint. The systems ahead on the route plotted in the game (`ahead`) are searched on their own (`search_route`: up to 100 by `system_id64`, nearest first; a full page leaves the systems from its last station's distance on unknown; each system's stations kept in memory 6 h; asked again only while no place is known before the first unknown system and it is within 50 jumps); the first place to sell on the route is listed first, after the system you are in (`routeJump`: jumps along the route); NavRoute.json changes invalidate `sell` |
| `app/ships.py` | Ships by journal symbol: name and landing pad size (EDCD coriolis-data, 2026-10-19) |
| `app/routes.py` | The route: worker-thread builder, storage (`route*` tables), `RouteView` with journal progress. Goal `transit` ("Get there"): Spansh's neutron route (`app.neutron.plot`), its waypoints as the stops with their jumps and supercharge flag (`route_stops.jumps`, `neutron`); a waypoint is passed once you arrive there, or further on, after the route was made. Goal `firsts`: a stop is done once you have been there; its chance comes from `app.discovery` (the cached answer, the lookup asked in the background through the plotted route's checker; until then what Spansh knew when the route was made: `route_stops.discovery`), and your arrival-star scan says whether you were first (`firsts_found`, `firsts_left`). Other goals: a stop left unfinished before the farthest one you arrived at since then counts as skipped (`passed`: not the button's skip, so no restore; flying back makes it the next stop again) |
| `app/fuel.py` | Fuel per jump of the current drive, learnt from its own `FSDJump`s (`fuel = k · (distance · mass)^power`, power by FSD size); the jump range at the mass aboard, scaled from `MaxJumpRange` (max fuel per jump from the curve, Guardian booster added flat) |
| `app/navroute.py` | The route plotted in the game (`NavRoute.json`): fuel forecast hop by hop (scooping at KGBFOAM stars), neutron stars / white dwarfs ahead, warnings, discovery chances |
| `app/shop.py` | The Shop tab (`ShopView`, `GET /api/view/shop[?item=<journal symbol>&carriers=true]`, catalog at `GET /api/shop/catalog`): with no item the nearest stations with a shipyard or outfitting and how many ships / modules Spansh knows they sell; with one, the stations selling exactly it (Spansh filters modules by name, class and rating but ignores the mount, so the symbol is checked here; only priced modules are asked for, as the free copies an ARX purchase adds are listed at no price and crowd the answer, and a renamed module under its old name too: `OLD_NAMES`, Fighter Hangar → Vessel Hangar), with price and the date of the shipyard / outfitting report; a commodity (`market` filter: the name, some in stock) with what the market sells a tonne for, its stock and the date of the market report; a material (never sold) the nearest material traders of its type (`material_trader` filter, stations only; Guardian and Thargoid materials are taken by none, so nothing is asked) and, a raw one, the nearest landable bodies with at least its `rich` share (`spansh.body_search`, the `materials` filter with a `share` range; 5 bodies, cached like the stations). Stations and carriers asked apart and picked as in `selling` (pad, docking rights, megaship age, carriers on request, the nearest hidden one as a hint). Told, not filtered: the navy rank a ship needs (journal `Rank` / `Promotion`), Powerplay or technology-broker unlocks, permit-locked systems. Answers kept in memory per item (1 h, within 20 ly); the catalog is `app/data/shop.json`, with EDSY's prices and figures (a ship's base price, performance and slots, a module's figures by kind), served gzipped by the catalog endpoint only (the event stream must not be compressed) |
| `app/discovery.py` | How likely a system is undiscovered: Spansh, then EDSM (worker thread, `discovery` cache table, 24 h); the chances by database state and distance from Sol / Colonia are measured against EDDN (4 h, 2681 systems; the star kind and the mass code turned out not to matter) (`tools/discovery_calibration.py`, numbers in the module docstring) |
| `app/neutron.py` | Spansh neutron plotter for the hop to the route's next stop (worker thread, `neutron_plan` table), progress from visits |
| `app/galaxy.py` | `GalaxyView`: visited systems with coordinates, the path in arrival order (broken at respawns), deaths, routes ahead, codex regions visited |
| `app/engineers.py` | The 38 engineers (25 ship, 13 suit and weapon; bases checked against EDSM on 2026-10-18) and your standing from `EngineerProgress` (`engineers` table) |
| `app/eddn.py` | Other players right now: the EDDN relay (ZeroMQ, zlib JSON) on a worker thread, only while `GET /api/view/live` is being asked for (hangs up 2 min after); a message with `StarPos` is a sign someone is in that system (arrived, scanned, codex, docked); the relay gives every uploader a new id every 3 minutes, so: dots for the last 5 min (each id where seen last: a player who moved across a change of ids has two), players counted per 3-minute stretch between changes (detected when every id heard in the last 30 s is new) and shown for the last full one; two ids sending the same events (not arrivals) twice are one player; ids live in memory only (7 min) |
| `app/regionmap.py` | Codex region of any coordinates: 2048×2048 run-length grid over the galactic plane (`app/data/regionmap.json`, EliteDangerousRegionMap, MIT); the system's region until a `CodexEntry` names it; `GET /api/regions` for the map |
| `app/enrich.py` | Community body data (Spansh, then EDSM) for the current system and any system opened by address, with its name and position (a system you have not been to gets a page from it alone), cached in `ext_*` tables; `prune` (at start): the bodies of systems not looked up for 30 days are dropped, the name and position stay, and opening the system asks again (`bodies_dropped`: the system view says `pending`) |
| `app/track.py` | Your path on planet surfaces (`surface_track`, outside the projections: the journal keeps no path): Status.json positions while the app runs, a point every 5 m on foot / 20 m in the SRV / 50 m in the ship (none above 5 km), in stretches (`seg`: a new one after leaving the surface, on another body, or when the app starts again); the service sends the globe new points at most every 5 s (`TRACK_SHOW_S`) |
| `app/globe.py` | The Surface tab's planet globe (`SurfaceView.globe`, landable planets with a known radius): your samples where the app recorded them (`sample_positions`), your path (`track`), your codex finds (`CodexEntry` latitude / longitude; a species whose samples are placed is left out), your landings and take-offs (`surface_marks`: `Touchdown`, `Liftoff` you flew yourself; the ship's own when recalled or dismissed are left out: off by 17–63 m from where it stood, they look like your position) and settlements (`ApproachSettlement`), your ship (`ship_here`: the latest touchdown or liftoff anywhere, if it was here, you are in this system and have not died since; `PlayerControlled: false` = recalled or dismissed), other players' finds grouped by name |
| `app/canonn.py` | Other players' finds on planet surfaces from Canonn (`getSystemPoi` by system name: its EDMC plugin users' bio samples and codex finds with coordinates, no names or dates), asked when the globe shows a planet of that system (`want_surface_finds`), on a worker thread; cached per system in `ext_surface` (24 h, a failed lookup retried after 1 h, keeping older points) |
| `app/datadir.py` | Where `data.db` lives. A folder chosen in Settings is noted in `location.json` in the standard folder (`%LOCALAPPDATA%\EDExplorerKit`, which never moves) with the folder to move from; the next start (`resolve`, before anything opens the database) copies it there with the SQLite backup API, checks it (`quick_check`) and deletes the old files; a failed move keeps the old database. `plan_move` refuses a folder that is the same, not a folder, cannot be created or written to, already holds a database, or lacks room. Sizes: the database with its WAL, the journals, the free space; `LARGE_DB_BYTES` (500 MB), `LOW_FREE_BYTES` (1 GB), `DB_PER_JOURNAL_BYTE` (1.2, measured) |
| `app/usersettings.py` | Highlight thresholds (`settings` table, `GET/PUT /api/settings`) and the journal folder chosen in the app (`journal_dir` row; ignored when the folder is set at launch) |
| `app/engineering.py` | Engineering goals (`engineering_goals` table: yours, never rebuilt) and your materials: `GET /api/view/engineering` (`EngineeringView`: goals, what they take against your stock, the stock and when the journal last listed it, and `fitted`: your current ship's modules with their blueprint and grade, from the latest `Loadout` and the `EngineerCraft` rolls after it, the kind by the module's symbol in `shop.json`, the blueprint by its journal name per kind, as some sensors share one), `POST /api/engineering/goals`, `PUT` / `DELETE /api/engineering/goals/{id}` (422 when a goal does not fit the catalog). Recipes from `app/data/engineering.json` (EDSY); grade N counted N rolls (an engineer's top access level), an experimental effect once, times the modules. Stock: the latest `Materials` event plus the deltas after it (`MaterialCollected`, `MaterialDiscarded`, `MaterialTrade`, `EngineerCraft`, `Synthesis`, `TechnologyBroker`, `MissionCompleted` rewards, `EngineerContribution` of materials, `ScientificResearch`), capped at each grade's storage; the projector answers those events with the `engineering` topic only (an own topic: nothing else goes stale). `body_materials`: a planet's elements for `BodyView.materials`, journal symbols and Spansh names alike. The catalog goes out with the Shop's (`ShopCatalogView.engineering`) |
| `app/bookmarks.py` | Your bookmarks (`bookmarks` table: made in the UI, not journal data, never rebuilt): a system, a body or a station (each once) or any number of places on a body (latitude, longitude); a tag (mining, bio, geo, trade, scenic, other; a station starts as trade) and a comment. A bookmark keeps the system's name and position (and the body's name), from the UI or from your journal / community data / another bookmark there, so places you have not been to show too. `here` / `add_here`: where you are (the journal's system, body and last station since arriving; Status.json for your spot and whether you are docked). `mark_stations` puts station bookmarks on the places of Where to sell and the Shop. The notes of before 2026-10-26 (`notes` table) became bookmarks tagged other, with their text as the comment (`migrate`, one transaction) |
| `app/facts.py` | Journal `Scan` → `BodyFacts`, JSON codec, `SystemFacts` loading |
| `app/game.py` | Whether the game is running (process list on Windows, else the journal's last `Shutdown`), pushed with the ingest state |
| `app/service.py` | Ingest thread, backfill, SSE fan-out. `set_journal_dir` (from `PUT /api/journal-dir`) queues a folder; the thread swaps the journal, Status.json and NavRoute.json readers and backfills the new folder. `IngestState` carries the folder, whether it exists, how many journal files it has (published when that changes: the game creating its folder), whether it is fixed, and the default. At start `_tidy` (prune, compact). Before reading journal files (at start, after a folder switch) `_hold_reason` weighs what is unread (× 1.2) against the free space on the database's drive (`space`) and, in the standard folder, against 500 MB until "keep it here" (`large`, meta `big_data_ok`, `POST /api/ingest/keep-here`): the read then waits (`IngestState.hold`, `hold_bytes`), checked again every rescan and on that request; Status.json and the rest go on. Sizes are measured every 30 s (`db_bytes`, `journal_bytes`, `free_bytes`) |
| `app/main.py` | FastAPI app: REST views, SSE stream, static frontend; CLI (`run`), exe niceties (opens the browser, a second start just opens the page). Listens on all interfaces by default (`--local`: loopback only) and logs the phone address; `_from_this_pc` tells the PC (loopback or one of its own addresses) from other devices |
| `app/models.py` | Domain dataclasses (`BodyFacts`, `SystemFacts`, `Species`, ...) |
| `app/schemas.py` | Pydantic view models (camelCase JSON) |
| `app/exobio/` | Species catalog (values, colony ranges) and prediction rules; `deduced_genera`: the genera surely there before DSS (as many possible as there are signals; measured on Spansh, numbers in its docstring); `variants.py`: the codex colour of a species on a body (the parent star's class for 64 species, a barycentre of stars counting as its heaviest star; a material for 26; group-B materials can tie, then every one present is a candidate), data in `app/data/codex_variants.json`; `odds.py`: the chance of each candidate species when the rules leave several of one genus (how often Canonn logged each on bodies with this atmosphere and body type, square-rooted; measured on Spansh, numbers in its docstring), data in `app/data/species_odds.json` |
| `app/values.py` | Cartographic value estimates (FSS / DSS) |

Rules:
- Journal files are the source of truth. Projection tables can be dropped and rebuilt.
- Body identity is `(SystemAddress, BodyID)`; `id64 = SystemAddress | (BodyID << 55)`.
- Order by event insertion order, never by timestamp (1-second resolution).
- Only the ingest thread writes journal-derived data (settings and route edits are short writes from the API; the route builder writes its own tables).
- The journal always wins over community data; community bodies are labelled with their source.
- 64-bit ids go to the frontend as strings.
- No code copied from GPL projects (EDMC-BioScan, EDMC-Canonn): facts are re-derived.

## Frontend (`frontend/`, Vite + React + TypeScript + Tailwind v4)

- Contract: `frontend/src/api/types.ts` mirrors `backend/app/schemas.py`.
- Pages have paths (`src/lib/router.ts`): `/system`, `/system/<SystemAddress>` (a system from the history), `/surface`, `/route`, `/session`, `/history`, `/galaxy`, `/stats`; `/` opens the tab used last. Clicks push the path, automatic switches (sampling → Surface) replace it. The backend serves `index.html` for these paths (`PageFiles` in `app/main.py`); the query (`?mock=1`) is kept.
- `GET /api/view/system|surface|session|sessions|sell|stats|history|navroute|galaxy`, `GET /api/status`, `GET /api/ingest`, `GET/PUT /api/settings`, `PUT /api/journal-dir` (`path`, null: the default folder; 422 `not_found`, 409 when set at launch, 403 from another device: a path from the network could point the app at someone's share), `GET /api/network` (`lan`, `urls`: the page on this PC's addresses, the default route's first; `thisPc`), `GET /api/regions` (the region grid, fixed, cached a day), `GET /api/view/live` (EDDN; the `live` topic is invalidated every 15 s while new signs come in; the client asks at least every 45 s to keep the listener on). `PUT /api/data-dir` (`path`, null: back to the standard folder; the database moves at the next start; 422 with the reason, 409 when set at launch, 403 from another device), `DELETE /api/data-dir/move` (stay), `POST /api/ingest/keep-here` (a big database may stay in the standard folder; 409 while the read waits for room).
- `GET /api/view/system?address=<SystemAddress>`: any system (also requests its community data): one from the history, or one you have not been to, from Spansh / EDSM alone (`lookup`: `pending` while asked, `missing` when they know no bodies, `offline` with `--offline`).
- Route: `GET /api/view/route`, `POST /api/route` (plan, 202; 409 with `--offline`), `DELETE /api/route`, `PUT /api/route/stops/{seq}` (`skipped` and/or `position`: skip, move), `DELETE /api/route/stops/{seq}` (remove), `POST /api/route/neutron` (Spansh neutron route to the next stop, 202; 409 with `--offline`), `DELETE /api/route/neutron`.
- Bookmarks: `GET /api/view/bookmarks` (every one, the latest first, with the light years to its system; `here`: what you can bookmark where you are), `POST /api/bookmarks` (`kind`, `systemAddress`, `bodyId`, `lat`/`lon`, `title`, `category`, `comment`, optional `systemName`, `bodyName`, `x/y/z`; a system, body or station already bookmarked gives its bookmark back; 422 for what cannot be bookmarked), `POST /api/bookmarks/here` (`what`: system, body, place, station; 409 when you are not there), `PUT /api/bookmarks/{id}` (`title`, `category`, `comment`; left out: unchanged), `DELETE /api/bookmarks/{id}`. The views carry them: `SystemView.bookmark` + `stations`, `BodyView.bookmark` + `places`, `NavHopView.bookmark`, `HistoryEntry.bookmark` + `innerBookmarks`, `GalaxyView.bookmarks`, `GlobeView.places`, the stations of `SellView` and `ShopView`.
- `GET /api/stream` (SSE): `hello`, `invalidate`, `status`, `ingest`, `ping`.
- `src/map/`: 3D orbit map (react-three-fiber); `src/map/visuals/`: procedural planet/star rendering. The ship: the body the game last put you at (`SystemView.shipBodyId`; the arrival star of `FSDJump`, `ApproachBody`/`Touchdown`, `SupercruiseExit` at a star or planet, `Location`) gets pulsing rings while you are there (`shipNear`) and a still dashed ring once you flew off (`LeaveBody`, a drop at a barycentre). In supercruise `CourseLine.tsx` draws a dashed line from it to the body targeted in the game (Status.json `Destination`: `LiveStatus.destinationSystem`/`destinationBody`). Neither the journal nor Status.json gives a position between bodies.
- The route plotted in the game (`src/screens/route/PlottedRoute.tsx`, the System tab's `PlottedStrip`): only what needs attention is shown — fuel and next-jump star warnings, systems ahead likely undiscovered (chance ≥ 50 %), those you bookmarked — else one calm line; the jump list is folded (the game lists the jumps too). The System tab's strip shows only with a warning or a likely first discovery.
- `src/screens/surface/globe/`: the planet globe on the Surface tab (lazy chunk `GlobeCanvas`; a Radar | Planet switch while you sample, the globe alone otherwise). The planet is the system map's procedural one, still and north up (`PlanetSurface`): the game does not share terrain, and says so under it; no day and night (the journal has no rotation phase). Its map is baked at 2048×1024 (the system map's 512×256 blurred at globe size); closer than that goes, `SurfaceDetail` makes up grain and bump in the surface shader (`EDK_DETAIL`: noise octaves from ~3 to ~800 px on screen, taken around a floating origin under the camera with whole lattice cells passed as integers, so float32 holds down to metres). Zoom goes by the height over the ground, from 5 radii down to 500 m (wheel and pinch handled by `CameraRig`; OrbitControls only turns, its dolly is off); the near plane, the turn speed and how high marks ride (`markLift`) follow the height, the grid hides close up. OrbitControls asks for a frame only after the camera moved 1e-3 radii (more than the whole view close up), so drags and their glide ask for frames themselves. On the ground (landed, on foot, in the SRV) the globe opens, or turns as you land, 4 km over you (`GlobeFocus.heightM`). Your path is one line draw (`pathLines`: the stored stretches, the latest drawn on to you within 2 km of its end). Game latitude / longitude on a unit sphere (`geometry.ts`: lat 0 / lon 0 at +x, east to the right); marks are WebGL points, one draw per layer, sized in CSS px and fading at the horizon; you (Status.json, heading), your ship, your landings and take-offs (plane icons, also in the legend and on cards: `LAYER_ICON`) and your bookmarked places (their tag's icon and colour) are HTML icons kept over their spot each frame; landing, take-off and ship icons within 10 m of each other stand in a row by time (`sideBySide`: you land and fly off from one spot), picked where they are drawn and, when moved aside, ringed themselves. A click or tap picks the marks within 14 / 22 px on screen (`pickNear`), nearest first; the card gives distance and heading from you (`lib/geo`) and a great-circle line, and bookmarks the mark (its name kept for life, settlements and finds; samples and life tagged bio). A tap on empty ground finds the spot under it (`groundAt`: the view's ray against the unit sphere) and offers to bookmark it; a button over the globe bookmarks where you stand. Every layer says where it comes from (`layers.ts`: the game now, your journal, recorded by the app, Canonn in violet); layers can be hidden (`edk.globe.hidden`); Canonn's finds are a list that filters the globe and picks the point nearest to you.
- `src/screens/route/map/`: 3D route map (lazy chunk). Galactic coordinates scaled to a fixed scene radius, z flipped (top view: core up, +x right); stops are screen-space dots picked on screen, labels placed without overlap.
- `src/screens/galaxy/map/`: 3D galaxy map (lazy chunk), 100 ly per scene unit, Sol at the origin; reuses the route map's camera, markers and labels. The galaxy behind is a procedural sketch (`backdrop.ts`), not game imagery. Codex regions (`regionLayer.tsx`): one quad on the galactic plane with the grid as an R8 texture; the shader draws a border where a pixel's on-screen neighbour lies in another region (crisp at any zoom) and tints visited regions; names sit at each region's point farthest from its border (`regions.ts`). Other players (`live.ts`, `liveLayer.tsx`): violet dots sized by players, fading with age; the layer is off by default (it makes the server download the whole EDDN feed). Engineers (`engineers.ts`, `engineerLayer.tsx`): orange rings, filled once unlocked. Hover cards sit beside their point (`LabelBox.beside`) in a layer above the legend; the dot nearest the pointer wins, yours on a tie. A click pins the card (`PickStore.selected`; a second click, empty space or Esc lets go): copy the system name, and open the system in a new browser tab (`/system/<address>`; one you have not been to only when Spansh / EDSM are asked: `GalaxyView.online`). Bookmarks: a ring around your systems holding some (the system's own tag colour, else pale yellow), a ringed dot for the others; the pinned card edits the system's bookmark and counts the others inside. Cards live in drei `<Html>` roots, which do not carry React context: the bookmark actions (`useBookmarkActions`) are handed down from `GalaxyMapCanvas`.
- `src/guide/`: the guide for new explorers. `topics.ts` holds the topic order, sections, the five-step loop and the outside sources (the same in every language); the texts are `t.guide` (`src/i18n/guide.ru.ts`, `.en.ts`, `.uk.ts`, part of the dictionaries). `GuideProvider` (around `App`) renders `GuideDialog` (a panel on the right, full screen on a phone; the app is inert behind it); `HelpTip` is the "?" next to a term (`useGuide().open(topic)`), `GuideButton` the book in the top bar. Facts in the texts were checked against the linked sources on 2026-10-19: change a number only with a source.
- `src/screens/shop/`: the Shop tab. `catalog.ts` finds ships, modules and commodities by words (word starts, initials such as FSD or MC, a few player names such as DBX; "5A", a class or a mount narrow the variant) and picks a module's variant (class, then mount, then rating, then guidance; another class keeps the mount). On a phone the lists fold and choosing one scrolls to the card. `ItemCard.tsx`: the ship card (blueprint `ShipSketch.tsx`: top view, side view under it, rear view beside that, in metres; `sketches.ts` takes the outlines traced from blueprint sheets in `outlines.json` for 35 ships (or from the game's schematics, without a rear view) and keeps its hand-drawn shapes, without a rear view, for the rest; base price, performance, slots, the navy rank against yours) and the module card (an icon by EDSY module type, figures formatted by `stats.ts`); arrows flip through ships (by price, the default, by name or by pad size; the ship list beside the card follows the same order and shows each pad and price; the type buttons above it, from `roles.ts` (the wiki's ship types), narrow both) or the modules of a group, and the results are asked for once the flipping settles (450 ms). Commodities are listed by market category (buttons), the rare ones apart; their card names the category and flips through it; a station shows the full price a tonne and the stock. Materials by type (raw, manufactured, encoded, and Guardian & Thargoid apart), a row per trader group in the game's order, each by grade; their card tells type, grade and group, whether traders take it, where it comes from (the wiki's list) and links the wiki page; a raw one adds "Plenty on planets" (bodies grouped by system, share, gravity, Ls).
- `src/screens/stats/share/`: "Share" on the Stats tab (`ShareButton` in the hero; the dialog is a lazy chunk with `modern-screenshot`). The tab's root is copied into an SVG foreignObject (styles and the Inter font inlined) and drawn on a canvas, at 2× while under 40 M pixels (16 M on touch screens: iOS Safari's limit). What stays out is hidden on the page itself for that moment (`data-snapshot` on the root; `[data-no-snapshot]` controls, `[data-snapshot-name]` on request, rules in `index.css`): the copy takes sizes as laid out, so leaving nodes out of the copy would leave gaps. Some browsers set the copy's text a hair wider than the page (not seen in Playwright's Edge or Chrome; reproduced there by adding word spacing to the clone in `onCloneEachNode`): a label exactly as wide as its box wrapped and ran into the next line, and a table's box got scroll bars. So every element whose text sits on one line on the page, and every `.truncate` box, is marked `data-snapshot-line` and kept on one line (`fits`: shown past its box instead of cut), and scroll boxes are `overflow: hidden` for the capture. One capture at a time. Layouts in the tab must not fill a line exactly with `ml-auto` either: the same hair wraps them.
- `src/screens/session/PastSessions.tsx` (+ `sessionList.ts`): past sessions at the bottom of the Session tab, sortable by any column (a first click sorts biggest or newest first, a second reverses it; ties go newest first, sessions without a pace last), a row opens what the session was made of. The latest session with no `Shutdown` is "Now" while the game runs (else it crashed) and its time counts up to now; "Per hour" is left out under 10 minutes.
- `src/settings/`: the settings dialog (`SettingsProvider` around `App`, `useSettings().open('journal')` from the top bar's journal strip): language, "On your phone" (`PhoneAccess.tsx`: a QR code of the address, drawn by `components/QrCode.tsx` with `uqr`, and firewall tips; only on the PC itself, opened at it with `open('phone')` from the welcome card), journal folder (`JournalFolder.tsx`, read-only on other devices), support. The highlight thresholds sit next to the bodies they highlight, on the System tab (`HighlightControl.tsx`: a panel without a backdrop, saved 400 ms after the last change). Data folder (`DataFolder.tsx`): where the database is, its size and the free space, a field to move it (at the next start, said with the folder it waits for), back to the standard folder. The top bar's room strip (`RoomStrip` in `components/TopBar.tsx`, `dataSize.ts`): a waiting read first (amber for no room, sky for a big database: "Keep it here" / "Choose a folder"; shown on a phone too, without buttons), then little room on the drive (below 1 GB; "Hide" until the free space halves, `edk.lowspace`), then a big database (500 MB, until "keep it here").
- First run: `components/Welcome.tsx` on the System tab until closed (`edk.welcome` in localStorage): what the app does with the journal, and the guide's five steps. The top bar's strip says when the journal folder is missing or has no journal files yet (start the game, or choose the folder). No guided tour (decided 2026-10-19).
- `src/screens/shop/EngineeringGoals.tsx`: the Shop's engineering goals card (folds, remembered per browser): the goals, a form of native selects (module kind, blueprint, grade now and wanted, experimental effect, how many), and the materials all goals take, what is short first; a material's name chooses it in the Shop. `src/components/PlanetMaterials.tsx`: a planet's elements as chips, the ones the goals still miss highlighted; on the System tab's body card and on the Surface tab.
- `src/components/Bookmark.tsx` (+ `bookmarks.ts`: tags with their icons and colours, names, `useBookmarkActions`): a bookmark shown and edited in place (`BookmarkBox`: the tag and your comment, or "Bookmark it"; the form picks a tag, names a place, takes the comment; Ctrl+Enter saves, Esc cancels; Delete in the form); `BookmarkEditor` takes the actions as a prop where there is no data store; `InlineBookmark` for a station in a list. `src/screens/bookmarks/BookmarksScreen.tsx`: the Bookmarks tab (bookmark where you are; search, kind and tag filters, newest or nearest first: light years, or metres to a place on the planet you are on; open the system, or the globe). Nine tabs: from xl the top bar shows the short names and the app's name gives way to its logo; a crowded bar (the demo's badge) scrolls its tabs instead of the page.
- The orbit tree comes from each body's `parents` chain (`Star` / `Planet` / `Null` = barycentre / `Ring`) plus `barycentres`; radii are not to scale.
- Layouts must hold on phones (360 px and up) in every language, not only on the desktop: let text wrap below `sm:` instead of `shrink-0`/`nowrap`, give grids an explicit `grid-cols-1`, put wide tables in a `relative overflow-x-auto` box. The 7-tab bottom bar uses `t.tabs.short` labels.
- Dark, modern, glanceable UI. Languages: English (default), Ukrainian, Russian — chosen in Settings, stored per browser;
  switching reloads the page. `src/i18n/ru.ts` is the original dictionary and defines the shape (`Strings`); `en.ts`
  and `uk.ts` follow it, checked by `dictionaries.test.ts`. Game names (systems, bodies, species, planet and star
  classes) stay in English in every language.

## Tools

- `backend/tools/codex_variants.py`: rebuilds `app/data/codex_variants.json` (the colour variants of Odyssey species) from Canonn's codex reference.
- `backend/tools/species_odds.py`: rebuilds `app/data/species_odds.json` (Canonn's reports of each species by atmosphere and body type, its colours added up) from Canonn's biostats.
- `backend/tools/ship_outlines.py` (`uv run --group tools`, OpenCV): rebuilds `frontend/src/screens/shop/outlines.json` from the wiki's blueprint sheets (35 ships): the white lines thresholded, filled, each view's silhouette traced; top and rear views symmetric halves; fractions of the ship's dimensions. `--screenshots <folder>` adds ships from `<symbol>.png` screenshots of the game's schematics (top and side views; the screenshots stay out of the repository); on a Cobra Mk III both ways agree to 0.98 / 0.95 IoU.
- `backend/tools/engineering_catalog.py`: rebuilds `app/data/engineering.json` from EDSY's `eddb.js` (Node evaluates it): the module kinds with blueprints (core, optional, hardpoints, utility, each by name), each blueprint's recipe per grade and each experimental effect's, materials by journal symbol; blueprints without a recipe left out; the materials FDevIDs lacks (new Thargoid ones) with EDSY's name, type and grade.
- `backend/tools/shop_catalog.py`: rebuilds `app/data/shop.json` (the Shop tab's ships and modules) from EDCD FDevIDs, under Spansh's names, leaving out suits, armour, the starter kit's `_free` copies and whatever Spansh has at no station; a ship's `fighter_bay` comes from the ships EDSY lists in its fighter hangars' `reserved`; a ship no station sells (out for ARX first: the Anaconda Mk II, in EDSY and not yet in FDevIDs) stays, marked `unsold`; ship-launched vessels in no source (`LAUNCHED`: the Nomad, ARX since 2026-06-30, under a symbol of our own) are added by hand with the hangar modules that carry them (`hangars`, buttons on its card); prices and figures from EDSY's `eddb.js` (evaluated by Node). Commodities from FDevIDs `commodity.csv` and `rare_commodity.csv` (the names Spansh's markets use), kept when some market has them in stock (379 in 2026-10, 139 rare; mission and salvage cargo never sold is left out); `--commodities` rebuilds only them. Materials from FDevIDs `material.csv` (137: type, grade, trader group; none for Guardian and Thargoid ones), with each one's "Known Sources" from its Elite Dangerous Wiki page, read as wikitext through the wiki's MediaWiki API (`api.php`, 50 pages a request; without such a list, the sentence of the game's description that says where it is found), and for raw elements the `rich` share: the 80th percentile on 2,000 landable bodies near Sol, Merope, Colonia and Synuefe EN-H d11-96 (Rhenium, Lead and Boron are on no planet); `--materials` rebuilds only them.
- `backend/tools/discovery_calibration.py`: measures the discovery chance against EDDN. `collect --hours N` stores what Spansh / EDSM knew of each uploaded route's systems and the later arrival-star scans (`WasDiscovered`), in `<data dir>/calibration/*.jsonl`; it resumes after a stop or a power loss (the time collected is counted from the records). `report [--neighbours]` prints first-discovery rates by database state, distance, star class and mass code, and the model's Brier score.


## Packaging

- **exe** (`packaging/`): PyInstaller one-file `EDExplorerKit.exe` with `frontend/dist` inside as `web/`
  (`ed-explorer-kit.spec`, built by `build-exe.ps1`; PyInstaller is the `build` dependency group).
  A console window shows the log; closing it stops the app.
- **Release** (`.github/workflows/release.yml`): a `v*` tag matching `app.__version__` runs the tests,
  builds the exe on Windows and publishes it as a GitHub release (`gh release create`).
- **Docker** (`Dockerfile`, `docker-compose.yml`): Node stage builds the UI, Python stage runs
  `python -m app.main --host 0.0.0.0`; journals mounted read-only at `/journals`, database in the
  `/data` volume (`EDEK_JOURNAL_DIR`, `EDEK_DATA_DIR`). Journal polling works through Docker Desktop
  bind mounts (no file-change notifications needed). The game process is not visible from the
  container, so "game running" falls back to the journal.
